## Things that were not obvious

### `es_CO` formats money as `12.500 $`

`NumberFormat.currency(locale: 'es_CO')` puts the symbol *after* the number.
That is correct formal Spanish typography per CLDR and it is not how anyone in
Colombia writes a price. The fix is to take the locale's separators
(`NumberFormat('#,##0', 'es_CO')`) and prepend the symbol by hand.

Caught by a unit test, not on device.

### `DateFormat` knows exactly one locale until you initialise it

`DateFormat('d MMM', 'en')` throws `LocaleDataException` at the first format
call. The only locale with built-in data is **`en_US`** — spelled exactly that.

The trap underneath: omitting the locale entirely *appears* to fix it, because
`DateFormat` then follows `Intl.defaultLocale`, which is `en_US` in a test
runner. It would have thrown on a phone set to Spanish. `NumberFormat` has no
such problem — its symbol data ships inside `intl`, which is why the currency
half worked while the date half did not.

Both are in ADR 0009.

### The Milestone 0 wildcard rule would have silently defeated the new one

This is the one worth remembering. M0 shipped:

```
match /{collection}/{docId} {
  allow read, write: if isOwner() && isKnownCollection(collection);
}
```

That wildcard also matches `transactions/{id}`. **Firestore evaluates every
matching rule and allows a write if *any one* of them allows it** — they are
OR-ed, not AND-ed. Adding a strict `match /transactions/{txId}` block above it
would therefore have enforced nothing at all, while looking completely correct
in the file and compiling and deploying without complaint.

The baseline block now carries `&& collection != 'transactions'`. Each
collection gets excluded from the catch-all as it graduates to real validation
— **remember this at Milestone 2 for `todos`.**

### Writes cannot go through `withConverter`

Every write carries `FieldValue.serverTimestamp()`, and a `FieldValue` is an
instruction to the server, not a value — it cannot live in a model object, so it
cannot come out of `toFirestore`. Reads use the converted reference, writes use
the raw one. The first draft of the repository had this wrong: it wrote through
the converter, which silently dropped both audit timestamps, and the new rules
would have rejected every single write with `permission-denied`.

### `createdAt` is null for the first few hundred milliseconds

Firestore's latency compensation puts a new document in the local cache and
fires listeners *before* the server stamps it. So on the writing device, the
first snapshot of a new transaction has `createdAt: null`. A non-nullable field
there would crash the list after every insert, on the one device that made it —
an intermittent-looking bug with a completely deterministic cause. The model's
nullable timestamps are the accurate type, not defensive padding.

## Changes after the first on-device run

Creating transactions worked on the first build. Three adjustments came out of
using it:

1. **Expense amounts are red.** They were white, which made income the only
   coloured row and left expenses looking like the neutral default. The red is
   `brandPrimaryLight`, matching the arrow already on that row — deliberately
   *not* `statusCritical`: an ordinary expense is not a critical state, and a
   screen where every row is the alarm colour has no alarm colour left for when
   something is genuinely wrong.

2. **The amount field groups thousands live.** Typing `100000` now shows
   `100.000` in the field itself. Unseparated, `100000` and `1000000` differ
   only by a zero nobody counts — people glance, assume, and log an amount ten
   times too big.

   The work is not the grouping, it is the caret. A `TextInputFormatter` returns
   text *and* a selection, and inserting a separator shifts every character
   after it one place right, so returning the old offset drops the caret in the
   wrong spot and typing into the middle of a number scrambles it. Positions
   cannot be mapped across the reformat because the separators move. What is
   stable is **how many digits sit left of the caret** — inserting a `.` does
   not change that count — so the caret is re-placed after the same number of
   digits. Four of the new tests are just that.

3. **A real bug, found while doing (2):** the edit form seeded the amount field
   with `Money.format()`, which includes the symbol, while the field's
   decoration *also* draws a `$` prefix — so editing a transaction showed
   `$ $12.500`. `Money.grouped()` now exists for the places that draw their own
   symbol.

### The console does *not* test your security rules

Worth writing down, because the intuition is completely reasonable and
completely wrong.

Trying to enter `-5` on the phone fails — but only because the amount field
offers a numeric keyboard and the formatter discards anything that is not a
digit. That is a **convenience**, not enforcement. The project's API key is
public (ADR 0008), so anyone can write to this collection with a plain HTTP
request and never touch the app.

The tempting next step is to type `-5` into the Firebase console instead and see
whether it is refused. It will not be — and that proves nothing. **The console's
data editor writes with admin credentials and bypasses security rules
entirely.** So does the Admin SDK, and so will the Cloud Functions in Milestone
3. Rules apply to *client* SDKs.

The tool that actually evaluates rules is the **Rules Playground** (Firestore →
Rules → Playground), which simulates an ordinary authenticated client. That
check is still outstanding:

- [ ] Rules Playground: an authenticated write with `amount: -5` is **denied**

## Savings goals and liabilities

Both built after the transactions slice was verified, copying its four-file
shape. The Finance tab is now a `DefaultTabController` with three tabs —
Transactions / Savings / Debts — rather than three routes, because they are
three views of one feature and the bottom nav should keep saying "Finance" once.

Three things worth recording:

### `FieldValue.increment`, not read-then-write

Adding to a savings goal and paying down a debt both adjust a number that
already exists. The obvious implementation reads the current value, adds to it,
and writes the result back — and it loses data: two devices that both read
50.000 and both add 10.000 each write 60.000, and one contribution silently
disappears.

`FieldValue.increment` is applied atomically **on the server**, so the result is
70.000 whatever the ordering. It also queues correctly offline, because what is
stored is the *instruction* rather than a computed value — it composes with
whatever happened elsewhere while the device was away.

The cost, noted in the repository: increment cannot clamp, because the server
applies it without reading anything back. So an overpayment can drive
`remainingAmount` negative. The form prevents it; enforcing it in the database
would need a real transaction, which trades away the offline behaviour for a
case that only arises from a typo. Recorded rather than papered over.

### Optional fields need three separate pieces of handling

A deadline that is optional in the model is not optional in practice unless all
three of these are right, and each fails differently:

1. **`toMap` omits the key** rather than writing `null` — a present-but-null key
   still counts as *present* to the rules' `hasOnly`/`hasAll` allowlist.
2. **`copyWith` needs an explicit `clearDeadline` flag.** Dart's
   null-means-unchanged convention has no way to express "remove this", so
   without the flag a deadline set once could never be removed.
3. **`update` must `FieldValue.delete()` the key.** An omitted key in an update
   leaves the old value in the document, so clearing the field in the form would
   appear to do nothing.

Liabilities have three optional fields and therefore three clear flags.

### The rules exclusion list is now three collections long

`transactions`, `savings`, `liabilities` are all excluded from the M0 catch-all
wildcard. Same reason as before — Firestore OR-s every matching rule — and it is
now a list rather than a single `!=`, which is the form it will keep. **Add
`todos` to it at Milestone 2.**

Deliberately *not* enforced in the liability rules: `remainingAmount <=
originalAmount`. `claude/data-model.md` suggests it, but interest and late fees
make a debt genuinely exceed what was borrowed, and an app that refuses to
record that is lying about the situation it exists to track.
