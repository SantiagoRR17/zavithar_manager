# Devlog — 2026-09-13

**Session goal:** Put the project under version control, then finish Milestone 1
by building the dashboard stat tiles.

Both done, plus a security audit that was not planned and turned out to be the
most valuable thing in the session. One planned item also turned out to be
impossible as planned.

## The repository did not exist

Three sessions of work — all of Milestone 0 and most of Milestone 1 — lived in a
single uncommitted copy on one machine. `CLAUDE.md` has said "feature branches
per milestone, small commits" since the planning phase, and both `.gitignore`
files were written in Milestone 0, so the intent was there from the start;
`git init` had simply never been run. Nobody noticed because nothing in the daily
loop of `flutter analyze` / `flutter test` / `flutter run` ever asks about git.

Worth recording as a category of mistake rather than a one-off: **a convention
written in a doc is not a thing that exists.** The `.gitignore` files were
evidence of the intention and were mistaken, by everyone reading the repo
afterwards, for evidence of the practice.

### Before the first commit

The point of checking first is that a commit is not a save — the history keeps
what you put in it, so deleting a leaked value later does not remove it. Swept
for anything covered by the no-personal-data rule:

| Check | Result |
|---|---|
| Owner email, real name | none anywhere |
| Machine paths (`C:\Users\...`) | none |
| `firebase-debug.log` (embeds the account email) | not present |
| `package-lock.json` (pnpm-only rule) | none |
| `.jks` / `.keystore` / `key.properties` | none |
| `app/android/local.properties` (SDK path, machine-specific) | present, correctly ignored |

120 files staged, no build artifacts. `firebase_options.dart` and
`google-services.json` are in, deliberately — client config, not secrets
([ADR 0008](../adr/0008-committing-firebase-config.md)).

### The commit author is part of the history

Git's global identity on this machine was the owner's real email, so every
commit would have carried it into a public repo permanently. The rule in
`CLAUDE.md` names "docs, comments, commit messages"; the *author* field is
metadata rather than a message, but it is exactly what the rule exists to
prevent, and fixing it after the fact means rewriting history.

Set repo-locally rather than globally:

```
git config --local user.email SantiagoRR17@users.noreply.github.com
```

GitHub still attributes the commits and still counts them as contributions.

### One import commit, not a reconstructed history

The work predates the repository. Splitting it into plausible per-feature
commits would have produced a history describing an order of work that never
happened — invented evidence, in the one file that is supposed to be the record.
A single honest import commit, with the small commits starting from here.

### The repo is public, and that moves a pending item to the top

The Firebase API key is now visible to anyone. Per ADR 0008 that is by design and
the key is not a secret — it identifies the project, it does not grant access to
it. But it means **the security rules are now the only thing standing between the
database and the internet**, and those rules have never been observed to reject
anything.

That check has been outstanding since 2026-08-25. It is no longer a tidiness
item.

## The Rules Playground cannot test these rules

This was on the plan as "ten minutes in the console". It is not possible, and the
way it fails is worse than not testing at all.

All three collections require:

```
data().createdAt == request.time && data().updatedAt == request.time
```

`request.time` is the instant the write reaches the server;
`FieldValue.serverTimestamp()` resolves to exactly it, which is what makes the
rule pass for an honest client and fail for one backdating its own history. In
the Rules Playground, timestamps are entered by hand through a date picker.
**There is no way to produce a value equal to `request.time`.**

So every simulated create and update is denied — on the timestamp, whatever else
is in the payload. Type `amount: -5`, see **denied**, conclude the amount rule
works. Nothing was tested. A security check that reports success without
exercising the thing it claims to check is worse than an absent one, because it
retires the question.

The Playground *is* sound for anything not involving timestamps: reading another
user's document, and the known-collection allowlist. Neither is the part that
needed proving.

The tool that actually evaluates these is the **Firestore emulator** with
`@firebase/rules-unit-testing`, which runs a real client SDK and therefore a real
`serverTimestamp()`. Everything it needs is already on the machine — Node 22,
pnpm 10.33, firebase-tools 15.28, Java 21. Next session.

## Dashboard stat tiles

The last outstanding piece of Milestone 1, built on the four-file shape the
finance slices established.

```
domain/       finance_summary.dart      — no Firebase import
application/  dashboard_providers.dart
presentation/ dashboard_screen.dart, widgets/stat_tile.dart
```

Balance across the top, this month's income and expense with their net, and
saved / debt-remaining with progress bars.

### Three listeners, not six

`financeSummaryProvider` opens nothing. It watches the same three
`StreamProvider`s the Finance tab watches, and Riverpod caches a provider per its
arguments — so both screens alive still means three Firestore listeners. A
dashboard that opened its own would have doubled the read cost of every change
for no benefit, which is NFR-5 money.

It is a plain `Provider` returning an `AsyncValue`, not a `StreamProvider`, since
there is no new stream — only a synchronous fold of three that already exist.

### Nothing here is stored, and the shortcut is a trap

A `balance` field on the user document is the obvious alternative, and it has to
be updated by every write to every collection. The first path that forgets — an
undo, an offline edit landing out of order, a document changed from the console —
leaves a stored total that disagrees with the rows that are supposed to explain
it, and no way to tell which is wrong. A total recomputed from its inputs cannot
drift from them. `claude/data-model.md` already says derived data is never
stored; this is why.

### Error has to be checked before loading

Folding three `AsyncValue`s, the natural order is wrong:

```dart
if (any.isLoading) return loading;   // ← spins forever
if (any.hasError)  return error;
```

A stream refused by a security rule is in the error state **permanently**. A
sibling that is merely slow is still loading. So the loading branch wins every
frame, and the genuine failure is never displayed — the screen just spins. Errors
are checked first, so a broken collection is reported rather than disguised as
slowness.

Related: the render decision uses `hasValue`, not `!isLoading`. A refreshing
stream is *both* loading and holding its previous value, and the tiles should
carry the last good numbers through a refresh instead of flashing back to a
spinner on every incoming snapshot.

### The month filter reads the wrong field if you are not careful

"This month" filters on `date` — when the money moved, chosen by the user — not
`createdAt`. January's rent typed in February has to count against January.

And the comparison is year *and* month. Matching on month alone folds last
September into this one, which is invisible for the first twelve months of use
and then silently wrong forever. Both have a test.

### Wrap, not GridView

`GridView.count` pins every cell to a single `childAspectRatio`, and these tiles
are not the same height — the ones with a progress bar and a two-line caption are
taller. A ratio suiting the tallest wastes space under the shortest; one suiting
the shortest overflows. `Wrap` lets each tile size itself. Columns come from a
`LayoutBuilder` at the 720px breakpoint `app_shell.dart` already uses, so the
layout changes shape once rather than twice.

Long amounts shrink via `FittedBox` rather than wrapping or clipping: COP figures
run to seven digits plus separators, and a number tile can compromise on anything
except the number being readable.

### Colour

A negative balance uses `brandPrimaryLight` — the same red as the expense rows —
deliberately not `statusCritical`. Being in the red is a state worth noticing,
not an emergency, and the alarm colour has to stay available for something
genuinely wrong. The sign (U+2212, matching `Money.formatSigned`), the trend icon
and the caption all say the same thing, so the colour is never the only signal.

Category colours are *not* used anywhere on this screen. They belong to the four
todo categories and reassigning them to finance figures would break "work is
orange" before Milestone 2 even starts.

### Empty state

A grid of `$0` tiles reads as a screen that failed to load. `isEmpty` is true only
when nothing is recorded in any of the three collections — notably **not** when
the balance happens to net to zero, which is real data and gets real tiles.

## Security audit of the pushed history

Run after the push, prompted by the right question being asked: *was what went
public actually checked?* The honest answer was that a targeted grep had been
run, not an audit — and the difference matters, because a commit is not a save.
History keeps what you put in it.

**Nothing confidential leaked.** Emails (content *and* commit metadata), private
keys, service accounts, tokens, mail configuration, credential-bearing URLs,
keystores — all absent. The one high-entropy string in the tree is a pub package
integrity hash. Full table in [ADR 0010](../adr/0010-public-repo-hardening.md).

But the audit found a real exposure, and the way it was confirmed is the point:
a REST call to the Identity Toolkit carrying the project's public API key, sent
from a plain terminal with no app and no signed package, came back **400
INVALID_LOGIN_CREDENTIALS — a 400, not a 403.** The key was accepted. Anything
the key can reach, the internet can reach.

With email/password sign-up open, anyone could create an account in the project.
They could not read the owner's data — the rules scope everything to
`request.auth.uid` and that part is sound — but they could write under their own
uid, exhaust the Spark plan's daily write quota (breaking the owner's own app),
and become a bill once Milestone 3 forces Blaze.

**Going public did not create this.** The key ships inside the APK; ADR 0008 says
so, which is exactly why it is not treated as a secret. Publishing the repo moved
the cost of discovery from "decompile an APK" to "open GitHub". The gap was just
as present while the repo was private — which is why making it private again
would not have fixed anything.

Fixed the same session: *Prevent account creation* in the Firebase console. And
**verified by watching it reject** — the same call now returns
`ADMIN_ONLY_OPERATION`. The project's own rule that an untested control is no
control applies to its own mitigations, not only to its rules.

## Two rough edges, found by using the screen

The dashboard was correct on first run and reconciled against its source:
`+$60.000 − $13.000 = $47.000`, both transactions dated 25 Aug, which is also
what demonstrates the month filter excluding them from September. Savings and
debt tiles matched their tabs.

Two things were wrong anyway, and neither was visible while reading the code:

1. **The Saved tile's icon was the brand red.** On that screen red already means
   expense — the arrow two rows above it — so a red piggy bank made savings read
   as a warning, while the amber debt tile beside it looked calmer. The thing you
   want more of cannot look worse than the thing you want less of. Now green, and
   the screen reads: green is yours, amber is owed, red is spent.

2. **`net >= 0` treated zero as positive**, putting a green tick and a "+$0" on a
   month in which nothing happened — approval of an achievement that does not
   exist. Three states now; zero is neutral and unsigned, because "+$0" implies a
   direction that $0 does not have.

Same lesson as 2026-08-25, when the transactions tab gave up its two rough edges
the same way. Building, analysing and testing a screen does not substitute for
holding it.

## Milestone 2 — todos

Built after the free-tier constraint landed, on the four-file shape the finance
slices established. Live list, category and status filter chips, create / edit /
delete with undo, follow-up linking.

### The rules gotcha, finally cashed in

`CLAUDE.md` has carried this reminder since Milestone 1: **add `todos` to the
exclusion list.** Firestore evaluates every matching rule and allows a write if
*any one* of them allows it, so the strict `match /todos/{todoId}` block added
this session would have enforced precisely nothing — while compiling, deploying
and reading as completely correct — had `todos` stayed in the
`match /{collection}/{docId}` catch-all. The exclusion list is now four
collections long.

Worth noting how the reminder survived a month and three sessions: it was
written into `CLAUDE.md` next to the milestone that would need it, not into a
devlog entry nobody re-reads.

### One rule deliberately looser than the finance blocks

`completedAt` is **not** pinned to `request.time`, unlike `createdAt` and
`updatedAt`. It is written once when a task is completed and then carried
unchanged through every later edit — so an update that merely fixes a typo
re-sends the original value, and `== request.time` would reject it. The type is
enforced; the exact instant is not worth making every edit of a finished task
fail.

`priority` is likewise left out of `hasAll` even though the app always writes
it. The rules stay one step looser than the client on purpose, so a document
written before a field existed does not become unwritable.

### Ordering is where a task list is quietly wrong or quietly right

Three decisions, each with a test:

- **Undated tasks sort last.** The obvious implementation treats a null deadline
  as the epoch, which sorts every undated task to the *top*, where it pushes
  everything actually due off the screen. Undated is not urgent, it is
  unscheduled.
- **`orderBy(createdAt)`, not `orderBy(deadline)`.** Firestore omits documents
  missing the ordered field entirely, so ordering by an optional deadline would
  silently hide every task without one — a bug that looks exactly like data
  loss.
- **A task with no `createdAt` yet sorts first.** Latency compensation means a
  just-typed task has a null server timestamp for a few hundred milliseconds;
  sorting it last would drop it to the bottom of the list and then make it jump.

### Filtering happens in memory, on purpose

A `where` clause per chip is the obvious approach and the worse trade here:
`category` + `orderBy(deadline)` needs a composite index per combination, and
every chip tap would re-read the documents. Firestore bills per read, so
server-side filtering on a personal task list costs **more**. FR-6's transaction
filters are the case that genuinely needs the index, because a ledger grows
without bound and a todo list does not.

### The status circle cycles

Pending to in progress to completed to pending, one tap each. A checkbox
expresses two of the three statuses and strands "in progress" inside the edit
sheet, three taps from the most frequent state change in a task list. The icon
changes shape as well as colour, and the tooltip says the state in words.

### Shared widgets moved to core/

`sheet_scaffold.dart`'s own doc comment said it had been "extracted after the
second form repeated it". Todos was the third, so the sheet chrome, the
empty/error states, the swipe-delete background, `OptionalDateField` and the
repository failure type moved to `core/`, losing their `Finance` prefixes. The
alternative was a `todos -> finance` import asserting a dependency that does not
exist.

`OptionalDateField` gained `withTime` on the way: "remind me on the 14th" with
no time silently means midnight, the one hour of the day a reminder is
guaranteed to be useless.
