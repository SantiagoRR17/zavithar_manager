## The repository did not exist

Three sessions of work — all of Milestone 0 and most of Milestone 1 — lived in a
single uncommitted copy on one machine. `CLAUDE.md` has said "feature branches
per milestone, small commits" since the planning phase, and both `.gitignore`
files were written in Milestone 0, so the intent was there from the start;
`git init` had simply never been run. Nobody noticed because nothing in the daily
loop of `flutter analyze` / `flutter test` / `flutter run` ever asks about git.

Worth recording as a category of mistake rather than a one-off: **a convention
written in a doc is not a thing that exists.** The `.gitignore` files were
evidence of the intention and were mistaken, by everyone reading the repo
afterwards, for evidence of the practice.

### The commit author is part of the history

Git's global identity on this machine was the owner's real email, so every
commit would have carried it into a public repo permanently. The rule in
`CLAUDE.md` names "docs, comments, commit messages"; the *author* field is
metadata rather than a message, but it is exactly what the rule exists to
prevent, and fixing it after the fact means rewriting history.

Set repo-locally rather than globally:

```
git config --local user.email SantiagoRR17@users.noreply.github.com
```

GitHub still attributes the commits and still counts them as contributions.

### One import commit, not a reconstructed history

The work predates the repository. Splitting it into plausible per-feature
commits would have produced a history describing an order of work that never
happened — invented evidence, in the one file that is supposed to be the record.
A single honest import commit, with the small commits starting from here.

### The repo is public, and that moves a pending item to the top

The Firebase API key is now visible to anyone. Per ADR 0008 that is by design and
the key is not a secret — it identifies the project, it does not grant access to
it. But it means **the security rules are now the only thing standing between the
database and the internet**, and those rules have never been observed to reject
anything.

That check has been outstanding since 2026-08-25. It is no longer a tidiness
item.

## The Rules Playground cannot test these rules

This was on the plan as "ten minutes in the console". It is not possible, and the
way it fails is worse than not testing at all.

All three collections require:

```
data().createdAt == request.time && data().updatedAt == request.time
```

`request.time` is the instant the write reaches the server;
`FieldValue.serverTimestamp()` resolves to exactly it, which is what makes the
rule pass for an honest client and fail for one backdating its own history. In
the Rules Playground, timestamps are entered by hand through a date picker.
**There is no way to produce a value equal to `request.time`.**

So every simulated create and update is denied — on the timestamp, whatever else
is in the payload. Type `amount: -5`, see **denied**, conclude the amount rule
works. Nothing was tested. A security check that reports success without
exercising the thing it claims to check is worse than an absent one, because it
retires the question.

The Playground *is* sound for anything not involving timestamps: reading another
user's document, and the known-collection allowlist. Neither is the part that
needed proving.

The tool that actually evaluates these is the **Firestore emulator** with
`@firebase/rules-unit-testing`, which runs a real client SDK and therefore a real
`serverTimestamp()`. Everything it needs is already on the machine — Node 22,
pnpm 10.33, firebase-tools 15.28, Java 21. Next session.

## Dashboard stat tiles

The last outstanding piece of Milestone 1, built on the four-file shape the
finance slices established.

```
domain/       finance_summary.dart      — no Firebase import
application/  dashboard_providers.dart
presentation/ dashboard_screen.dart, widgets/stat_tile.dart
```

Balance across the top, this month's income and expense with their net, and
saved / debt-remaining with progress bars.

### Three listeners, not six

`financeSummaryProvider` opens nothing. It watches the same three
`StreamProvider`s the Finance tab watches, and Riverpod caches a provider per its
arguments — so both screens alive still means three Firestore listeners. A
dashboard that opened its own would have doubled the read cost of every change
for no benefit, which is NFR-5 money.

It is a plain `Provider` returning an `AsyncValue`, not a `StreamProvider`, since
there is no new stream — only a synchronous fold of three that already exist.

### Nothing here is stored, and the shortcut is a trap

A `balance` field on the user document is the obvious alternative, and it has to
be updated by every write to every collection. The first path that forgets — an
undo, an offline edit landing out of order, a document changed from the console —
leaves a stored total that disagrees with the rows that are supposed to explain
it, and no way to tell which is wrong. A total recomputed from its inputs cannot
drift from them. `claude/data-model.md` already says derived data is never
stored; this is why.

### Error has to be checked before loading

Folding three `AsyncValue`s, the natural order is wrong:

```dart
if (any.isLoading) return loading;   // ← spins forever
if (any.hasError)  return error;
```

A stream refused by a security rule is in the error state **permanently**. A
sibling that is merely slow is still loading. So the loading branch wins every
frame, and the genuine failure is never displayed — the screen just spins. Errors
are checked first, so a broken collection is reported rather than disguised as
slowness.

Related: the render decision uses `hasValue`, not `!isLoading`. A refreshing
stream is *both* loading and holding its previous value, and the tiles should
carry the last good numbers through a refresh instead of flashing back to a
spinner on every incoming snapshot.

### The month filter reads the wrong field if you are not careful

"This month" filters on `date` — when the money moved, chosen by the user — not
`createdAt`. January's rent typed in February has to count against January.

And the comparison is year *and* month. Matching on month alone folds last
September into this one, which is invisible for the first twelve months of use
and then silently wrong forever. Both have a test.

### Wrap, not GridView

`GridView.count` pins every cell to a single `childAspectRatio`, and these tiles
are not the same height — the ones with a progress bar and a two-line caption are
taller. A ratio suiting the tallest wastes space under the shortest; one suiting
the shortest overflows. `Wrap` lets each tile size itself. Columns come from a
`LayoutBuilder` at the 720px breakpoint `app_shell.dart` already uses, so the
layout changes shape once rather than twice.

Long amounts shrink via `FittedBox` rather than wrapping or clipping: COP figures
run to seven digits plus separators, and a number tile can compromise on anything
except the number being readable.

### Colour

A negative balance uses `brandPrimaryLight` — the same red as the expense rows —
deliberately not `statusCritical`. Being in the red is a state worth noticing,
not an emergency, and the alarm colour has to stay available for something
genuinely wrong. The sign (U+2212, matching `Money.formatSigned`), the trend icon
and the caption all say the same thing, so the colour is never the only signal.

Category colours are *not* used anywhere on this screen. They belong to the four
todo categories and reassigning them to finance figures would break "work is
orange" before Milestone 2 even starts.

### Empty state

A grid of `$0` tiles reads as a screen that failed to load. `isEmpty` is true only
when nothing is recorded in any of the three collections — notably **not** when
the balance happens to net to zero, which is real data and gets real tiles.
